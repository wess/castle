# Hosts & routing

Castle gives every `*.local` name a 2-layer story:

1. **mDNS publish** — avahi announces the name → host IP.
2. **nginx vhost** — Castle generates a vhost so traffic on `:80` for that
   name reaches your service.

You can opt into just (1) (mDNS-only alias) or use both (full route).

## Two kinds of entries

The **Domains** page lists two kinds of things:

- **Routes** (mDNS + nginx) — created with a backend `host:port`.
  Castle writes `/etc/castle/nginx-routes/<hostname>.conf`.
- **mDNS aliases** (mDNS only) — created without a backend. Castle just
  publishes the name; you provide the routing some other way (or there
  isn't any — useful for naming things you SSH into).

## Create a route

In the Domains UI:

- **Hostname**: `git` → resolves to `git.local`
- **Backend**: `127.0.0.1:3001`
- **WebSocket upgrade**: on (default)

Click **Add**. Castle:

1. Inserts a `host_routes` row.
2. Adds `git.local` to `/etc/castle/mdns-aliases`.
3. Writes `/etc/castle/nginx-routes/git.local.conf`.
4. `sudo systemctl restart castle-mdns.service`.
5. `sudo systemctl reload nginx`.

Within ~5s, `http://git.local` resolves to your host and nginx proxies to
the backend.

## Multi-location routes

A single hostname can fan out to multiple backends by URL pattern. Edit a
route and add **extra paths**:

| Pattern                              | Backend           | WS  |
| ------------------------------------ | ----------------- | --- |
| `~ ^/[^/]+/[^/]+\.git(?:/\|$)`       | `127.0.0.1:3000`  | off |
| `/`                                  | `127.0.0.1:3001`  | on  |

The default `location /` is rendered last so it acts as the catch-all.
This is what Tangle needs: `git push`/`git clone` over HTTP hits port
3000 (smart-HTTP), everything else hits port 3001 (web/API).

## Generated nginx config

The rendered vhost looks like:

```nginx
# generated by castled — do not edit by hand
server {
    listen 80;
    listen [::]:80;
    server_name git.local;

    client_max_body_size 1024m;

    location / {
        proxy_pass http://127.0.0.1:3001;
        proxy_http_version 1.1;
        proxy_buffering off;
        proxy_request_buffering off;
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
    }
}
```

The `$connection_upgrade` variable is defined once in
`/etc/nginx/conf.d/castle-upgrade.conf`:

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

## Manual nginx sites

If someone hand-drops a config in `/etc/nginx/sites-available/`, Castle's
Domains page shows it under **Manual nginx sites** with:

- The file name
- The parsed `server_name` values
- A switch to enable/disable (symlink in `sites-enabled/`)
- An eye icon to view the raw config

Castle never **modifies** these files — they're managed by humans. The UI
is a window into them.

Enable/disable goes through the `castle-nginx-site` helper (sudoers
restricted), so castled never directly touches root-owned files.

## How mDNS works

`castle-mdns.service` is a small bash wrapper around `avahi-publish-address`:

```bash
DEFAULT_IFACE=$(ip route show default | awk '/^default/ {print $5; exit}')
IP=$(ip -4 -o addr show dev "$DEFAULT_IFACE" | awk '{print $4}' | cut -d/ -f1 | head -1)
```

It picks the IP attached to the **default-route** interface, not `hostname
-I` (which can pick `lxcbr0` or a docker bridge — these aren't routable
from the LAN). For each line in `/etc/castle/mdns-aliases` it spawns:

```bash
avahi-publish-address -R <hostname> $IP
```

…and waits on all PIDs. The service restarts whenever the file changes
(Castle calls `sudo systemctl restart castle-mdns.service` after every
add/remove).

## Resolution from clients

- **macOS, iOS**: native mDNS — `git.local` just works.
- **Linux desktop**: install avahi-daemon + nss-mdns; same as macOS.
- **Windows**: install Bonjour (Apple's iTunes installer includes it) or
  use the IP directly.
- **Android**: erratic. Most apps respect mDNS; some don't.

If a name doesn't resolve, check from the Castle host first:

```bash
ssh wess@host 'avahi-resolve -n git.local'
```

If that returns the right IP but your laptop doesn't see it, the problem
is on your laptop or the network — not Castle.

## Cold-start latency

First request to a `.local` hostname can take ~5s because of:

1. mDNS query (one round trip + retry budget)
2. ARP for the resolved IP
3. Cold TCP + nginx + upstream

Subsequent requests are fast. If you don't want to wait, hit the IP
directly: `curl -H "Host: git.local" http://192.168.4.87/`.

## Common problems

- **`.local` resolves to `10.0.3.1` (LXC bridge) or `172.17.0.1` (docker0)**
  Your `castle-mdns` script is picking the wrong interface. Castle's
  current version uses the default-route IP; if you're on an older
  version, update.
- **`502 Bad Gateway`** — nginx is reaching out to the backend but it's
  not running. Check the container/process behind the route is up.
- **Multiple routes for the same hostname** — nginx logs a "conflicting
  server name" warning at reload and uses the first one. Disable manual
  sites for any hostname now managed by Castle.
- **Daemon can't reload nginx** — sudoers entry missing. Run install.sh
  on the box to refresh, or add manually:
  `wess ALL=(root) NOPASSWD: /bin/systemctl reload nginx`.
